# 008 — Dynamic System Prompt

## Objective

Replace the hardcoded 3-sentence system prompt with a dynamic, section-based prompt
builder that gives the LLM rich environment context and tool usage guidance — improving
its ability to use tools effectively while keeping the architecture extensible for future
per-model prompts.

## Context

The current nexus system prompt is ~3 sentences inlined in `app.py`. The exec tool's
auto-generated description (function signatures) carries most of the tool documentation
weight, but there's no environment context (container details, mounted dirs, working
directory), no behavioural guidance, and no exec tool *strategy* (patterns, when/how to
compose operations). Nextgen has a proven section-based prompt with soul, environment, and
tools sections. Tau demonstrates co-located tool documentation (`_guidelines`) that
lives with the tool definition and gets aggregated into the system prompt.

## Requirements

- MUST build the system prompt dynamically from discrete sections (identity, environment, tools)
- MUST include an identity section with personality/behaviour guidance (hardcoded constant)
- MUST include an environment section with runtime context: working directory, container
  details, mounted paths, model name, exec Python path
- MUST include a tools section with exec tool strategy — patterns, composition guidance,
  available functions, and behavioural rules
- MUST keep tool function signatures auto-generated from introspection (existing
  `_generate_tool_docs()` pattern in `exec/tool.py`)
  - AC: Adding a new exec tool function automatically updates both the tool API description
    and the system prompt
- MUST separate the tool API description (sent in `toolConfig`) from the system prompt tool
  strategy (usage patterns, when/how to compose)
- SHOULD add `_guidelines` metadata to exec tool functions, aggregated into the system
  prompt's tools section
  - AC: Each exec tool can declare behavioural guidelines that appear in the system prompt
- MAY support per-model prompt variations in future (not implemented now, but architecture
  should not preclude it)
  - AC: The prompt builder accepts a model identifier parameter even if unused initially
- MUST NOT load external files at runtime for prompt content (all hardcoded/generated)
- MUST produce a single string suitable for the Bedrock `system` field

## Technical Design

1. **New module: `agent/src/archie_agent/prompt.py`** — single module with a
   `build_system_prompt()` function that assembles sections. No class hierarchy; pure function.

2. **Section assembly:** Sections joined with `\n\n` separators, no XML tags. Three sections:
   identity (constant), environment (dynamic), tools (static strategy + dynamic guidelines).

3. **Tool metadata on exec tools:** Add a `_guidelines` attribute (tuple of strings) to each
   tool function in `exec/tools/fs.py` and `exec/tools/shell.py`. These are collected by a
   `get_tool_guidelines()` helper in `exec/tools/__init__.py` which calls `get_all_tools()`
   (not `_TOOLS` directly) to ensure registration is triggered, then extracts `_guidelines`
   from each function. This is distinct from the host-side `ToolRegistry` which holds the
   single `exec` ToolSpec.

4. **Two layers of tool documentation:**
   - **System prompt** → strategy/patterns (how to compose, when to use exec, examples) +
     aggregated per-tool guidelines
   - **Tool API description** (`ToolSpec.description` in `toolConfig`) → function signatures
     + one-line docs (already auto-generated by `_build_exec_description()`)

5. **`build_system_prompt()` signature:**
   ```python
   from archie_agent.exec.tools.fs import _WORKSPACE

   def build_system_prompt(model_name: str, workspace_dir: str = str(_WORKSPACE)) -> str:
   ```
   Accepts model name for future per-model branching. Workspace dir defaults to
   `str(_WORKSPACE)` from `exec/tools/fs.py` (the single source of truth for `/workspace`)
   and is parameterised for testing.

6. **Integration:** `app.py` calls `build_system_prompt(model.name)` instead of the inline
   string. `AgentHarness` unchanged (it accepts `system_prompt: str`).

7. **Guideline ordering:** `get_tool_guidelines()` iterates tools in sorted name order
   (matching `_generate_tool_docs()`) to ensure deterministic output and non-flaky tests.

8. **`_guidelines` attribute safety:** The `@tool` decorator in `exec/tools/__init__.py`
   returns the function unchanged, so attributes set after decoration persist.
   `inspect.signature()` and `inspect.getdoc()` are unaffected.

## Milestones

### 1. Add `_guidelines` metadata to exec tools

**Approach:**
- Each tool function in `exec/tools/fs.py` and `exec/tools/shell.py` gets a `_guidelines`
  attribute — a tuple of strings set after the function definition
- New helper `get_tool_guidelines() -> list[str]` in `exec/tools/__init__.py` calls
  `get_all_tools()` (which triggers registration imports), then iterates the returned dict
  in sorted key order, collecting `_guidelines` tuples from each function
- Functions without `_guidelines` are silently skipped (forward-compatible)
- Guidelines are short imperative sentences (Tau's style):
  - `read`: "Use `read` to examine files — don't shell out to cat/head/tail"
  - `write`: "Use `write` only for new files or complete rewrites"
  - `edit`: "Prefer `edit` over `write` for modifying existing files — it's safer and shows a diff"
  - `grep`: "Use `grep` for searching file contents by pattern"
  - `glob`: "Use `glob` for file discovery by name pattern"
  - `shell`: "Use `shell` for commands that aren't covered by other tools (build, test, git)"
- The `@tool` decorator returns `fn` unchanged so `_guidelines` persists; `inspect.signature`
  and `inspect.getdoc` remain unaffected

**Tasks:**
- Add `get_tool_guidelines() -> list[str]` to `exec/tools/__init__.py`
- Add `_guidelines` tuples to `read`, `write`, `edit`, `grep`, `glob` in `fs.py`
- Add `_guidelines` tuple to `shell` in `shell.py`
- Add unit test in `tests/test_exec_tools.py` verifying `get_tool_guidelines()` returns
  a non-empty list containing expected entries (assert on set membership, not order)

**Deliverable:** Each exec tool declares its own behavioural guidelines, extractable via
`get_tool_guidelines()`.

**Verify:** `uv run pytest tests/test_exec_tools.py -v -k guidelines` passes.

### 2. Create `prompt.py` with section-based builder

**Approach:**
- New module `agent/src/archie_agent/prompt.py`
- Three internal pieces: `_IDENTITY` constant, `_build_environment()`, `_build_tools()`
- `_IDENTITY` content (concise, ~10-15 lines):
  - You are Archie, a coding assistant running in a sandboxed container
  - Be concise and direct, no filler
  - Use tools proactively — investigate before answering
  - Return structured data from exec, use print() for debug
  - Implement what's asked, no more
  - A successful write/edit means the change is applied — don't re-read to verify
- `_build_environment(model_name, workspace_dir)` returns:
  - Model name
  - Workspace directory (the project root)
  - Exec interpreter path: report `_PYTHON` from `exec/tool.py` — this tells the LLM
    where exec code runs (e.g. "/opt/archie/venv/bin/python"), not a version number
  - Container context: isolated Docker (Debian), destroyed after session
  - Mounted paths: /workspace is the project root
- `_build_tools()` returns static strategy section + dynamic guidelines:
  - Strategy patterns (adapted from nextgen's `_TOOLS_SECTION`):
    - Search/explore: grep → collect paths → read
    - File creation: write then verify via shell (test/lint)
    - Multi-op composition: `asyncio.gather` for independent operations
  - Notes: paths relative to workspace root, errors raise exceptions, shell returns
    `{"stdout", "stderr", "exit_code"}`
  - Appends aggregated guidelines from `get_tool_guidelines()` as a bullet list
- Import `_WORKSPACE` from `exec.tools.fs` for the default `workspace_dir` value
- ⚠️ Don't duplicate function signatures — those belong in the tool API description

**Tasks:**
- Create `agent/src/archie_agent/prompt.py`
- Implement `_IDENTITY` constant with the content listed above
- Implement `_build_environment(model_name, workspace_dir) -> str`
- Implement `_build_tools() -> str` with strategy patterns + `get_tool_guidelines()` call
- Implement `build_system_prompt(model_name, workspace_dir="/workspace") -> str`
- Create `tests/test_prompt.py` with tests for:
  - Identity section present in output
  - Environment section contains model name and workspace dir
  - Tools section contains strategy patterns and tool guidelines
  - Full prompt is a single non-empty string

**Deliverable:** `build_system_prompt("claude-sonnet-4-20250514")` returns a well-structured
prompt with all three sections including aggregated tool guidelines.

**Verify:** `uv run pytest tests/test_prompt.py -v` passes.

### 3. Wire into `app.py` and remove inline prompt

**Approach:**
- Import `build_system_prompt` from `archie_agent.prompt` in `app.py`
- Replace the inline prompt string with `build_system_prompt(model.name)`
- No changes to `AgentHarness` — it already accepts `system_prompt: str`
- The WS integration test and harness tests create their own harness with custom prompts
  so they won't be affected
- ⚠️ If any test asserts on exact system prompt text from `app.py`, update it

**Tasks:**
- Replace inline prompt in `app.py` with `build_system_prompt(model.name)` call
- Remove the now-unused inline string and its comment
- Run full test suite to confirm no regressions

**Deliverable:** The application uses the dynamic prompt builder; no prompt text remains
in `app.py`.

**Verify:** `uv run ruff check && uv run pytest -q` — all tests pass, lint clean.
